## 목적
문서를 보고하기 전에, 반복될 지적을 미리 잡고 회의에서 나올 질문을 준비한다.

## 우리가 만드는 것
관찰된 문서 요구사항 체크리스트. 사람에 대한 프로파일이 아니다.
성격·성향·심리를 추정하는 문장을 어떤 파일에도 쓰지 않는다.
"꼼꼼한 편", "숫자에 민감", "완벽주의", "~한 스타일" 같은 표현을 금지한다.

## 입력
state/intake.json 이 유일한 재료다. 필수는 문항 1과 10 둘뿐이다.
skipped 배열에 있는 문항의 내용을 추측으로 채우지 않는다.

## 절차
1. 문진관을 단독 실행한다
2. 체크리스트 초안을 보여주고 승인을 받는다
3. 승인 후에만 save_rubric 을 호출한다
4. 승인 후 편집관·질문관·답변관을 동시에 실행한다
5. 종합해서 save_review 를 호출한다

## 모드
intake.json 의 draft 가 "없음" 이 아니면 검수 모드, "없음" 이면 가이드 모드.
가이드 모드에서 초안을 대신 써주지 않는다. 무엇을 어디에 써야 하는지만 알려준다.

## 근거 규칙
- 모든 체크리스트 항목에 근거 문항 번호와 신뢰등급을 단다
- 신뢰등급은 도구가 계산한 값을 그대로 쓴다. 직접 판단하지 않는다
- 모든 지적에 rubric_id 를 단다. 체크리스트에 없는 걸 지적하지 않는다
- 근거를 못 대는 질문은 speculative: true 로 표시한다. 지우지 않는다
- 초안에 없는 숫자·사실·인과를 만들어 넣지 않는다

## 개인정보 규칙
사람 이름은 이니셜로만. 회사·제품·프로젝트 고유명사는 일반명사로 바꾼다.

## 중단 규칙
- 같은 에이전트가 3회 실패하면 멈추고 사람을 호출한다
- 체크리스트 항목이 2개 이하면 부족한 상태 그대로 보고한다. 채워 넣지 않는다
- high 등급 항목이 하나도 없으면 그 사실을 halts 에 기록한다

## 실습 2 · 계약

산출물의 서식을 먼저 정합니다. 기구 설계로 치면 도면을 먼저 그리는 일입니다.

```
schemas/review.schema.json 을 만들어줘. JSON Schema 2020-12 형식이다.

최상위 필수: mode, reviewer, evidence, rubric, questions, total_prep_minutes
- mode: "review" 또는 "guide"
- evidence: { answered(정수), skipped(정수배열), high_count(정수), improve_by(정수배열) }
- rubric[]: { id, title, confidence(high|medium|low), score(정수), basis(문자열배열), action }
- marks[]: { rubric_id, line(정수 또는 배열), issue, fix }     ← review 모드에서만
- guide[]: { section, must_include(배열), rubric_id(배열) }     ← guide 모드에서만
- questions[]: { q, basis(배열), confidence, speculative(불리언),
                 answer, missing(배열), prep_minutes, past_count(선택) }
- halts: 문자열 배열
```

---

## 짚고 갈 것

계약에는 **`basis` 가 비었는데 `speculative` 가 false 인 경우** 를 막을 방법이 없습니다.
JSON Schema 로는 "둘 중 하나는 참이어야 한다" 를 표현하기 까다롭습니다.

그래서 5장에서 만들 `save_review` 도구가 이걸 **따로 검사**합니다.

> **계약이 잡는 것과 도구가 잡는 것이 다릅니다.**
> 계약은 모양을 잡고, 도구는 의미를 잡습니다. 둘 다 필요합니다.
